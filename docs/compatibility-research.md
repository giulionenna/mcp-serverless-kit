# OAuth compatibility research: AgentCore Gateway + Cognito

Research date: 2026-10-08. This is a docs-based assessment, not a test result; neither ChatGPT nor Claude compatibility has been tested. Compatibility remains conditional on live preflight checks below. A known OAuth metadata gap may block MCP clients even though Cognito supports PKCE at its authorization endpoint.

Update 2026-10-09: the original AWS deployment completed and live Cognito
discovery confirmed the missing S256 field. The current implementation adds an
[AWS-only OAuth adapter](oauth-compat.md), with a separate OAuth metadata server
identifier and Cognito JWT token issuer. The native-discovery discussion below
describes the original direct-Gateway path. Adapter/client compatibility remains
subject to the [live verification gates](verification.md).

## Findings

- **Cognito can serve as the OAuth/OIDC authorization server; AgentCore Gateway is the protected resource.** Configure the gateway's JWT authorizer with Cognito's OIDC discovery document, normally `https://cognito-idp.<region>.amazonaws.com/<user-pool-id>/.well-known/openid-configuration`. That is distinct from the gateway's OAuth Protected Resource Metadata (PRM) document at `https://<gateway-host>/.well-known/oauth-protected-resource`. AgentCore returns the PRM URL in `WWW-Authenticate`; clients use PRM to discover the authorization server and scopes, then query Cognito discovery for its authorize/token endpoints. AWS documents both layers and scope challenges. [AWS inbound authorization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-inbound-auth.html) [Cognito endpoints](https://docs.aws.amazon.com/cognito/latest/developerguide/federation-endpoints.html)

- **Cognito's app client must be provisioned ahead of the OAuth flow.** Cognito documents app-client creation/configuration and callback URL allowlists, but its published authorization server endpoint list has authorize, token, userInfo, revoke, OIDC discovery, and JWKS—no dynamic client-registration endpoint. Treat DCR as unavailable with Cognito and provision a public/confidential app client yourself. [Cognito endpoints](https://docs.aws.amazon.com/cognito/latest/developerguide/federation-endpoints.html) [CreateUserPoolClient API](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolClient.html)

- **Claude remote MCP OAuth has a documented static-client path, but public-client support is not established by the cited help page.** Anthropic says Claude supports DCR and users can supply a custom client ID and client secret when DCR is unavailable. Its callback URL is `https://claude.ai/api/mcp/auth_callback`; Anthropic says it may change to `https://claude.com/api/mcp/auth_callback` and recommends allowlisting both. The docs do not explicitly establish whether Claude's manual credentials form accepts a client ID with no secret, so a Cognito public client needs direct setup validation. [Anthropic: Building Custom Connectors via Remote MCP Servers](https://support.anthropic.com/en/articles/11503834-building-custom-connectors-via-remote-mcp-servers)

- **ChatGPT supports predefined OAuth clients, but the callback depends on OAuth metadata.** OpenAI's MCP auth guide says use the exact redirect URI displayed in the MCP server management page. If the authorization server does not meet issuer-identification requirements (`authorization_response_iss_parameter_supported` plus a matching `iss` on every authorization response), ChatGPT uses `https://chatgpt.com/connector/oauth/{callback_id}`; otherwise it uses `https://chatgpt.com/connector_platform_oauth_redirect`. Cognito's compatibility with the stable-callback issuer requirements must be checked; plan to register the exact callback ChatGPT displays. OpenAI supports predefined OAuth clients and common token endpoint methods including `none`, but the custom-server guide does not explicitly confirm that a static public Cognito client with no secret can be entered in the UI. Treat public-client setup as an item to verify. [OpenAI: Authentication](https://developers.openai.com/plugins/build/auth) [OpenAI: Add custom MCP server](https://developers.openai.com/api/docs/guides/custom-mcp-server)

- **Cognito's PKCE implementation and its discovery metadata are separate compatibility requirements.** AWS documents that Cognito supports PKCE for authorization-code grants. OpenAI's MCP auth guide requires the authorization server metadata to advertise `code_challenge_methods_supported` containing `S256`; it says MCP servers are unsupported when that field is absent or does not include `S256`. A developer report in Anthropic's official Claude Code repository describes Cognito discovery omitting this field despite PKCE working at Cognito's endpoints; a later report describes the same gap with AgentCore Gateway. These are issue reports, not AWS guarantees about current behavior, so inspect the live pool's discovery document before proceeding. If the field is missing, treat ChatGPT OAuth as blocked under OpenAI's published requirement, and treat Claude compatibility as unverified. [AWS Cognito PKCE support](https://docs.aws.amazon.com/cognito/latest/developerguide/federation-endpoints-oauth-grants.html) [OpenAI MCP auth requirements](https://developers.openai.com/plugins/build/auth) [Anthropic Claude Code issue #13275](https://github.com/anthropics/claude-code/issues/13275) [Anthropic Claude Code issue #35846](https://github.com/anthropics/claude-code/issues/35846)

- **Cognito redirect rules fit both clients, subject to metadata preflight.** Cognito accepts HTTPS callback URLs and rejects authorization requests whose `redirect_uri` is not in that app client's `CallbackURLs`; localhost is a development exception. A single Cognito app client can list multiple callback URLs, so the Claude callback(s) and actual ChatGPT callback can coexist. Use authorization-code grant with PKCE. Cognito returns a refresh token for authorization-code grants without `offline_access`; requesting that scope has no effect, and refresh-token lifetime is configured on the app client. OpenAI's separate app setup guidance says refresh support can depend on `offline_access`, so confirm ChatGPT accepts Cognito's behavior and discovery metadata before claiming durable refresh compatibility. [Cognito authorization endpoint](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html) [Cognito token endpoint](https://docs.aws.amazon.com/cognito/latest/developerguide/token-endpoint.html) [CreateUserPoolClient API](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_CreateUserPoolClient.html) [OpenAI MCP app setup](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)

- **JWT validation needs deliberate client/audience/scope choices.** AgentCore can validate allowed `client_id`, `aud`, and scopes. Configure the allowed client to match the Cognito app client ID. OpenAI says ChatGPT sends `resource` in authorization and token requests and expects it to be echoed into the access-token audience; Cognito supports RFC 8707 resource binding and sets `aud` from `resource`, so this part appears aligned in published docs. Cognito authorization-code access tokens with a `resource` parameter can carry `aud`; without resource binding, do not assume `aud` exists. Define a least-privilege custom resource-server scope for gateway access rather than granting broad Cognito admin scope. [AWS inbound authorization](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-inbound-auth.html) [OpenAI: Authentication](https://developers.openai.com/plugins/build/auth) [Cognito authorization endpoint](https://docs.aws.amazon.com/cognito/latest/developerguide/authorization-endpoint.html) [Cognito resource-server scopes](https://docs.aws.amazon.com/cognito/latest/developerguide/cognito-user-pools-define-resource-servers.html)

- **Client registration and gateway invocation are separate concerns.** Claude's connector handles/obtains OAuth tokens and calls the MCP URL. Its API MCP connector beta specifically requires the caller to acquire and refresh tokens externally, passing `authorization_token`; that API behavior should not be conflated with Claude.ai custom connectors. [Anthropic MCP connector API docs](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)

## Published costs relevant to a near-zero-cost target

- AWS currently publishes AgentCore Gateway API invocations at **$0.005 per 1,000**, Search API at **$0.025 per 1,000**, and tool indexing at **$0.02 per 100 tools indexed per month**. The Gateway page says consumption-based, no upfront/minimum, with standard network transfer charges; policy/identity and CloudWatch may add charges depending on features/use. [AWS AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)
- Cognito user-pool cost depends on feature plan and monthly active users; AWS directs users to the live Cognito pricing page. Client-credentials M2M grants add Cognito charges. For this human sign-in pattern, do not claim “free” or a total without region, feature plan, MAU, Lambda usage, logs, data transfer, and current pricing inputs. [Cognito cost tracking](https://docs.aws.amazon.com/cognito/latest/developerguide/tracking-cost.html) [Cognito OAuth grants](https://docs.aws.amazon.com/cognito/latest/developerguide/federation-endpoints-oauth-grants.html) [Cognito pricing](https://aws.amazon.com/cognito/pricing/)
- The requested “near-zero” cost is plausible at low usage based on published per-invocation pricing, but it is not a guaranteed total. A gateway with one or two OAuth sign-ins and modest Lambda use still has other metered components, especially logs and network transfer. Treat the published rates as an estimate input, not a fixed monthly quote.

## Implementation implications

1. Create Cognito user pool/domain, resource-server scope(s), and a pre-registered app client. Prefer authorization code + PKCE for public clients; keep any client secret in the server-side confidential-client configuration, never in a distributed client.
2. For Claude custom connectors, allowlist `https://claude.ai/api/mcp/auth_callback` and (future-proofing per Anthropic) `https://claude.com/api/mcp/auth_callback`; enter the pre-registered credentials using Claude's custom-client option if DCR is unavailable. Confirm whether the UI permits a no-secret public client before choosing one.
3. For ChatGPT, create/configure the MCP app first, then add the exact callback URL ChatGPT displays (callback-ID-specific unless Cognito meets OpenAI's issuer-identification requirements). Confirm the static/public-client configuration path and refresh behavior. Cognito's authorization-code flow returns refresh tokens without requesting `offline_access`.
4. **Preflight before client setup:** fetch the exact Cognito `/.well-known/openid-configuration` and require `code_challenge_methods_supported` to contain `S256`; verify `scopes_supported` advertises the requested scopes and that the MCP scope is allowed on the Cognito app client; fetch the gateway `/.well-known/oauth-protected-resource` and confirm its `authorization_servers` entry exactly equals Cognito's `issuer`, plus the expected resource and scopes. OpenAI requires `S256` in authorization-server metadata, while user reports indicate Cognito may omit it. If absent, do not describe this Cognito configuration as compatible with ChatGPT; find a supported metadata workaround or another provider. Then verify actual authorization-code + PKCE and refresh flows in each client before describing compatibility as tested.
